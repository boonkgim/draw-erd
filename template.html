Notation

  • Crow's foot at the many end. || exactly one · o| zero or one · o< zero or many · |< one or many.
  • A dashed line means the child's foreign key is nullable — the relationship is optional.
  • PK primary key · FK foreign key · U unique · a trailing ? on a column name means nullable.
  • The letter after a foreign key is what happens on delete — §4's referential action, in the gutter rather than in the crow's foot, which has no notation for it. FK·R is RESTRICT: the parent row cannot be deleted while this one points at it. FK·C is CASCADE: deleting the parent deletes this row. One per foreign-key column, so the number of marks is larger than the number of foreign keys wherever a composite spends two columns on one reference, and larger again than the number of edges wherever a self-reference is listed rather than drawn — say all three counts here, because they differ.
  • A badge beside a table's name says the one thing about that table its columns cannot show, from a vocabulary closed to three. contended — §9's contention table names this row as a serialisation point, held under SELECT … FOR UPDATE for the read and the insert that depend on it. ledger — §4 rejects every update and delete on the table, so what a reader would look for as a column is a sum over its rows, and its footer says so. external — a table this model does not own. The badge is text, never colour, and it is a view of the document like every other mark here: a table §4 and §9 say none of those things about carries no badge, however busy it looks.
  • A composite foreign key is one edge: the child box lists its columns and the footer names the reference.
  • A dashed box is a table this model does not own. user is drawn because two tables reference it; it is generated by an auth library.
  • Header colour groups tables by subject area, and the grouping is also stated in each table's name, so colour is never the only carrier of meaning.
  • The page opens at Keys only, which leaves each box with what a relationship is made of: its primary key, every foreign key, and every column in a unique — including the ones that only exist to be half of a composite reference — on a tighter grid, because short boxes do not need the room tall ones do. It opens there because the first question a diagram answers is which tables reach which. Data model is the selection §4 makes; All columns is every column §4 lists, and the count beside each table name says which you are reading. Expanding any one table opens the diagram back onto the roomy grid.
  • Both grids put the same tables in the same cells, and every edge keeps the side of the box it leaves from in either one, so the two are the same picture at two sizes rather than two pictures. Nothing is laid out automatically: both grids are placed by hand.

Not shown

  • Anything the data model does not settle. Listed here rather than invented.
  • A self-referencing foreign key, if the model has one: list the column in its box and say so here. The routing connects two boxes, so a self-loop would be a line struck through one.
  • Derived values, columns the model deliberately refuses, check predicates (§6) and indexes (§7). A balance the model derives rather than stores is not listed here: its ledger box states it positively in its own footer, where it reads as a design rather than as an omission.
  • Which referential actions can ever fire. The rules themselves are on the canvas beside every foreign key — see FK·R and FK·C above — but whether anything ever deletes such a parent row is a property of the write paths, not of §4.
